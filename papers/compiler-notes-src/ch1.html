第 1 章

编译器概览

Introduction: What a Compiler Is and How It Works

这一章回答三个问题：编译器是什么、它周围有谁、它内部怎么工作。我们会跟着一条赋值语句 a[index] = 4 + 2 走完翻译的全过程，看它如何从一串字符变成一棵树、再变成几条机器指令。最后，我们会遇到一个哲学味十足的问题——用 C 写的 C 编译器，是怎么编译出来的？

对话：编译器只是一个"运行按钮"吗？

学生：我一直以为 IDE 里那个绿色的三角形就是编译器。

教授：那个按钮背后至少藏着五个程序：预处理器、编译器、汇编器、连接器、装入程序。编译器只是其中一个，而且它自己内部又分成六个阶段。

学生：六个阶段？把代码翻译成机器码，为什么要分这么多步？

教授：问得好。这正是本章的关键问题之一。答案和你写大程序的经验是一样的：一次只解决一个问题。先把字符切成单词，再把单词组织成结构，再检查结构的意思，最后才生成代码。每一步都有清楚的输入和输出，才可能把一个 10 万行的程序做对。

学生：10 万行？编译器有那么大？

教授：课件上说的是 1 万到 100 万行。GCC 的代码量以千万行计。但别怕——原理只有几页纸，而且我们有一个只有几百行的玩具编译器 TINY 可以整个读完。

1.1　为什么需要编译器

关键问题：人写的程序，机器怎么执行

人类习惯用接近数学和自然语言的记法表达算法；机器只执行编码成数字的指令。这中间的鸿沟由谁来填、怎样填？

定义

编译器（compiler）是一种计算机程序，它把用一种语言写的程序翻译成另一种语言的等价程序。它的输入叫源程序（source program），用源语言写成，通常是 C、C++ 这样的高级语言；它的输出叫目标程序（target program），用目标语言写成，通常是目标机器的目标代码（object code）或机器代码。编译器是非常复杂的程序，规模从一万行到一百万行代码不等。

课件里的例子非常典型。源程序是一行 Pascal 风格的赋值：

I := I0 + L * 2

目标程序则是一段与之等价的机器代码，用汇编形式写出来是：

MOVF  id3, R2      ; 把变量 L 装入寄存器 R2
MULF  #2.0, R2     ; R2 = R2 * 2.0
MOVF  id2, R1      ; 把变量 I0 装入 R1
ADDF  R2, R1       ; R1 = R1 + R2
MOVF  R1, id1      ; 把结果存回变量 I

注意几件事：一行源代码变成了五条指令；变量名 I、I0、L 变成了 id1、id2、id3（它们在符号表里有登记）；运算顺序遵守了"先乘后加"。这三件事分别对应本章后面要讲的代码生成、符号表和语法分析。

三层阶梯：从机器语言到高级语言

为了理解编译器为什么会出现，回顾一下程序设计语言的三级阶梯：

层次写法（"把 2 放进 X"）优点缺点
机器语言
machine language		C7 06 0000 0002机器直接执行费时、乏味、极易出错
汇编语言
assembly language		MOV X, 2用符号表示指令和地址，编写速度和正确率大幅提升；至今仍在使用仍难写难读；机器依赖——换一种 CPU 就要重写

最早的程序是直接用机器语言写的：程序员写下的是表示机器操作的数字码。汇编语言把指令和内存位置换成了符号形式，由汇编器（assembler）把符号翻译回数字。这是一次巨大的进步，但汇编语言仍然难写、难读，而且是机器依赖的（machine dependent）。

高级语言则更进一步：它的记法接近数学或自然语言，独立于任何特定机器。但它带来两个立刻要回答的问题，课件用一句话点了出来——翻译可能吗？生成的目标代码高效吗？这两个问题分别引出了编译理论（回答"可能吗"）和优化技术（回答"高效吗"）。

补充：第一台"翻译机"的怀疑者

1950 年代，当 John Backus 的团队提出要为 IBM 704 写一个 FORTRAN 编译器时，很多程序员并不相信"自动生成的代码"能比得上手写汇编。这个项目耗费了约 18 人年。它的成功证明了高级语言在实践上是可行的，也把"编译器能不能生成高效代码"这个问题变成了此后几十年编译研究的主线。

理论基础

编译器的理论基础来自一个意想不到的方向：语言学家 Noam Chomsky 对自然语言结构的研究。他按照文法的复杂程度和识别它们所需的算法，把语言分成了四类，这就是乔姆斯基层次（Chomsky hierarchy）。课件给出了完整的四类，我们把它整理成一张表：

类型名称规则形式识别它的机器在编译器中的用途
0 型短语结构文法 / 无限制文法任意形式图灵机理论上限，实践中不用
1 型上下文有关文法xSy → xAy（S 只有在上下文 x、y 中才能推出 A）线性有界自动机很少直接使用
2 型上下文无关文法S → A（S 无条件地推出 A）下推自动机描述程序的语法（第 3 章起）
3 型正则文法S → Aa（等价于正则表达式）有穷自动机描述单词的结构（第 2 章）

对编译器来说，最有用的是最下面两层。上下文无关文法（context-free grammar）描述程序的语法，由此发展出的分析问题（parsing problem）成了编译理论的标准组成部分；有限自动机和正则表达式则给出了表达程序设计语言单词结构的符号方法——这正是下一章的全部内容。第三块理论基础是优化技术（代码改进技术），它回答"高效吗"这个问题。

提示：为什么单词用 3 型、语句用 2 型

一个直觉：识别标识符只需要"记住当前读到了哪一步"（有限状态就够了）；识别 ((a+b)*c) 这样的括号嵌套，则必须数括号——需要一个栈。有限自动机没有栈，下推自动机有。所以单词交给正则表达式和有限自动机，语法交给上下文无关文法和下推自动机（也就是带栈的分析程序）。

1.2　编译器的亲戚们

编译器很少单独工作。从你写下源文件到程序真正跑起来，中间有一整条流水线，编译器只是其中一环。

解释器

解释器（interpreter）和编译器一样是语言翻译程序，区别在于：源程序被立即执行，而不是等整个翻译完成之后再执行。一门语言既可以被解释也可以被编译，课件把 BASIC、LISP、Java 归入解释型，把 FORTRAN、C、C++ 归入编译型。解释器和编译器共享许多操作——它同样要做词法分析、语法分析、语义分析，只是最后一步不是"生成代码"而是"直接执行"。

补充：Java 到底是编译还是解释

课件把 Java 列为解释型语言，这是教材成书年代的说法。今天的 Java 是两者的混合：javac 把源程序编译成与机器无关的字节码，JVM 再解释执行字节码，并在运行中把热点代码即时编译（JIT）成机器码。Python、JavaScript 也都走类似的混合路线。"编译"和"解释"与其说是语言的属性，不如说是实现的选择。

汇编器

汇编器（assembler）是特定计算机的汇编语言的翻译程序。由于汇编语言只是机器语言的符号形式，翻译很简单。有时编译器会生成汇编语言作为目标语言，然后由汇编器完成到目标代码的最后一步——GCC 就是这样做的。

连接器

连接器（linker）把分别编译或汇编得到的多个目标文件收集到一个最终的可执行文件里，并把它们与标准库函数的代码、操作系统提供的资源（内存分配器、I/O 设备等）连接起来。历史上这曾是编译器的主要活动之一，现在被拆分成了独立的程序。

装入程序

目标代码中的内存引用是相对于一个尚未确定的起始位置的——程序可能被放在内存的任何地方。装入程序（loader）把所有可重定位的地址解析成相对于给定起始地址的绝对地址。装入过程通常是操作系统的一部分。

预处理器

预处理器（preprocessor）是编译器在翻译开始之前调用的独立程序。它可以删除注释、包含其他文件（#include）、执行宏替换（#define）。宏是对重复出现的一段文本的简写。

编辑器、调试器与其他

源程序用编辑器写成，产生标准的 ASCII 文件。现代编译器往往和编辑器等程序捆绑成集成开发环境（IDE）：编辑器懂得语言的格式，能在你输入时报告错误，并能从编辑器内部直接调用编译器。调试器（debugger）用来找出已编译程序中的执行错误，它需要编译器保留行号、变量名和过程名等源代码信息，能在断点处暂停执行并显示调用的函数与变量的当前值。此外还有描述器（profiler，统计程序各部分的执行时间）和项目管理程序（如 make）。

1.3　翻译过程：六个阶段

关键问题：怎样把翻译这件大事拆成小事

从字符串到机器码的距离太远，不可能一步跨过去。编译器把翻译分成一系列阶段（phase），每个阶段接受前一阶段的输出、产生一种更接近目标的中间表示。问题是：分成哪几步？每一步的输入输出是什么？

我们用同一个例子贯穿六个阶段——课件里的 C 语句：

a[index] = 4 + 2

阶段一：扫描程序

扫描程序（scanner）读入源程序——一个字符流——执行词法分析（lexical analysis）：把字符序列收集成有意义的单元，称为记号（token），并判断是否有词法错误（例如出现了语言中不存在的字符）。我们的例子被切成 8 个记号：

记号的文本类别记号的文本类别
a标识符 identifier=赋值 assignment
[左方括号 left bracket4数 number
index标识符 identifier+加号 plus sign
]右方括号 right bracket2数 number

注意扫描程序把 index 五个字符看成一个单元，也把空格全部丢掉了。它不关心这些记号排列得对不对——那是下一个阶段的事。扫描程序是整个第 2 章的主题。

阶段二：分析程序

分析程序（parser）接收记号形式的源代码，执行语法分析（syntax analysis）：确定程序的结构，这和给自然语言的句子做语法分析（主语、谓语、宾语）很像；同时判断是否有语法错误。分析的结果表示为分析树（parse tree）或语法树（syntax tree）。

分析树忠实记录了语法分析的每一步，但它太啰嗦了：expression → identifier → a 这一串有三层，真正的信息只有"这里是标识符 a"。抽象语法树（abstract syntax tree，简称语法树）是分析树所含信息的浓缩：去掉只有一个孩子的中间层，把运算符提到父节点的位置。

课件在这里留了一个思考题："如何在内存里存储树的结构？"答案在 1.4 节：每个节点是一个结构体，字段里存着指向孩子的指针。

阶段三：语义分析器

程序的语义（semantics）就是它的"意思"，它决定了程序运行时的行为。大多数语言有一些在执行之前就能确定的特性，叫静态语义（static semantics），典型的两项是声明和类型检查。语义分析器（semantic analyzer）计算出的额外信息叫属性（attribute），它们作为注释或"装饰"加到树上，得到注释树（annotated tree）。

请体会一下语义分析器要做的推理：查符号表得知 a 是"整数数组"、index 是"整数"；数组用整数做下标是合法的，结果是"整数"；4 + 2 两边都是整数，和也是整数；赋值两边都是整数，合法。如果 a 是一个 float 而不是数组，语义分析器就会在这里报错。

阶段四：源代码优化程序

最早可以做优化的时刻就是语义分析之后：有些改进机会只依赖于源代码本身，与目标机器无关。不同编译器在优化的种类和放置的位置上差别很大。课件把这一阶段的输出叫做中间表示（intermediate representation, IR）或中间代码。

我们例子里的机会显而易见：4 + 2 可以由编译器预先算出来。这种优化叫常数合并（constant folding，也译常量折叠）。在注释树上做这件事，就是把右边那棵子树"坍缩"成它的常量值：

阶段五：代码生成器

代码生成器（code generator）接收中间代码，为目标机器生成代码。课件为了可读，把目标代码写成汇编语言；大多数真实编译器直接生成目标代码。到了这一步，目标机器的性质变得重要起来：要使用目标机器的指令集；要知道数据的表示方式——整数和浮点数各占几个字节或几个字。

课件的例子假设：&a 表示 a 的地址（数组的基地址）；*R1 表示间接寄存器寻址（以 R1 中的值为地址去访问内存）；机器按字节编址；整数占 2 个字节。于是 a[index] = 6 变成：

MOV  R0, index    ;; 把 index 的值装入 R0
MUL  R0, 2        ;; R0 乘以 2（每个整数占 2 字节）
MOV  R1, &a       ;; 把 a 的地址装入 R1
ADD  R1, R0       ;; R1 = R1 + R0，得到 a[index] 的地址
MOV  *R1, 6       ;; 把常数 6 存入 R1 所指的内存

请特别注意第二条指令：为什么要乘 2？因为 a[index] 的地址是"基地址 + index × 每个元素的大小"，而每个整数占 2 字节。这就是"目标机器的性质变得重要"的具体含义——换一台整数占 4 字节的机器，这里就得乘 4。

阶段六：目标代码优化程序

目标代码优化程序（target code optimizer）在目标代码上做改进，包括：选择更好的寻址方式以提高性能；用更快的指令代替慢指令；消除冗余或不必要的操作。对上面的代码，三处改进合在一起：

MOV  R0, index    ;; 把 index 的值装入 R0
SHL  R0           ;; 左移一位 = 乘 2，但移位比乘法快得多
MOV  &a[R0], 6    ;; 用"基址+变址"寻址方式，一条指令完成存储

五条指令变成了三条：乘法换成了移位（更快的指令）；地址计算与存储合并成一条带变址寻址的指令（更好的寻址方式），顺便消除了 R1 这个临时寄存器（消除冗余）。

提示：分阶段的真正理由

六个阶段各有一种输入表示和一种输出表示：字符 → 记号 → 树 → 注释树 → 中间代码 → 目标代码。每一步只需要理解相邻的两种表示。这种"一次只做一件事"的分解，是所有大型软件都在用的思想，编译器只是它最经典的范例。分阶段还带来了另一个好处，1.5 节讲前端/后端时会看到。

1.4　编译器中的主要数据结构

编译器各阶段使用的算法和支撑这些阶段的数据结构之间有很强的相互作用：算法必须以高效的方式实现，所以数据结构的选择非常重要。课件列出了六种主要的数据结构。

记号

扫描程序把字符收集成记号时，用符号方式表示记号——即一个枚举类型的值，该枚举类型代表源语言的记号集合。有时还需要保留字符串本身或由它推导出的其他信息：标识符记号关联的名字、数记号的值。在大多数语言里，扫描程序一次只需要生成一个记号（单符号先行，single symbol lookahead），因此可以用一个全局变量保存当前记号的信息。

语法树

语法树构造成标准的基于指针的结构，在分析进行时动态分配。整棵树可以用一个指向根节点的变量来保存。每个节点是一个记录（结构体），其字段表示分析程序和语义分析器收集的信息——有时这些字段本身也是动态分配的。

typedef struct treeNode {
    struct treeNode *child[3];    /* 指向孩子的指针 */
    struct treeNode *sibling;     /* 指向兄弟的指针 */
    NodeKind  nodekind;           /* 语句、表达式…… */
    ExpType   type;               /* 语义分析器填入的属性 */
    int       lineno;
} TreeNode;

TINY 编译器中语法树节点的（简化）定义——回答了 1.3 节"如何存储树"的思考题

符号表

符号表（symbol table）保存与标识符相关的信息：函数、变量、常量和数据类型。它与编译器的几乎每个阶段都有交互：扫描程序或分析程序把标识符放进去，语义分析器加入类型信息，代码生成器查询地址。插入、删除和访问操作都必须高效，标准的数据结构是哈希表（hash table，课件也叫杂凑表）。

常数表

常数表（literal table）保存程序中用到的常量和字符串。快速插入和查找是关键，但不需要支持删除——一个常量整个编译过程中都可能被引用，把它放在一个地方还可以避免重复存储。

中间代码

取决于中间代码的种类和所做的优化，它可能保存为文本字符串数组、临时文本文件或结构的链表。

临时文件

历史上计算机的内存不足以在编译期间把整个程序保存在内存里，于是用临时文件保存中间步骤的产物。如今内存限制已经小得多，但编译器偶尔仍会在某些步骤生成中间文件，一个例子是反填（backpatching）：生成跳转指令时目标地址还不知道，先留空，等地址确定后再回头填上。

1.5　编译器结构中的其他问题

分析与综合

编译器中分析源程序以计算其性质的操作属于分析（analysis）部分：词法分析、语法分析、语义分析。产生翻译后代码的操作属于综合（synthesis）部分：代码生成。优化步骤可能同时涉及分析和综合。

前端与后端

另一种更重要的划分：只依赖于源语言的操作叫前端（front end），只依赖于目标语言的操作叫后端（back end）。这种结构对编译器的可移植性（portability）特别重要。

补充：M + N 而不是 M × N

假设你要支持 M 种源语言和 N 种目标机器。如果每个组合各写一个编译器，需要 M × N 个。但如果所有前端都产生同一种中间表示（IR），所有后端都从这种 IR 出发，那么只需要 M 个前端和 N 个后端，共 M + N 个。这正是 GCC 和 LLVM 的结构：Clang、Rust、Swift 等前端都生成 LLVM IR，再由同一批后端翻译到 x86、ARM、RISC-V。中间代码就是让前端和后端"解耦"的那个接口。

遍

编译器在生成代码之前，常常要把整个源程序处理好几次，每一次叫一遍（pass）。遍和阶段不一定对应：一遍可以包含多个阶段，一个阶段也可以跨多遍。取决于语言，编译器可以是单遍的——编译效率高，但目标代码效率不高；Pascal 和 C 都被设计成可以单遍编译。大多数带优化的编译器使用多遍，典型的分组是：① 扫描和分析；② 语义分析和源代码级优化；③ 代码生成和目标代码优化。

语言定义

一门语言的词法、语法和语义的描述汇集在语言参考手册（language reference manual）或语言定义中。设计新语言时，语言定义和编译器往往一起开发；更常见的情形是为一门已经有定义的知名语言写编译器。

出错处理

出错处理是编译器最重要的功能之一。错误可能在几乎每个阶段被检测出来；编译器报告的错误都是静态错误（编译时错误）。生成有意义的错误信息很重要；错误处理器为不同的阶段和情况提供不同的操作。

提示：分辨"语法错误"和"语义错误"

少一个右括号、多一个分号、关键字拼错——分析程序能发现，是语法错误。类型不匹配、变量未声明、给数组整体赋一个整数——结构完全合法，但"意思"不对，是语义错误。作业 1.3 要求你各举两个例子，并观察你常用的编译器是先报完所有语法错误再报语义错误，还是混在一起报——后者说明它在一遍里同时做了语法分析和语义分析。

1.6　自举与移植

关键问题：编译器本身用什么语言写？

用 C 写 C 编译器，听起来像是"用一本词典的定义去解释这本词典"。第一个 C 编译器从哪里来？把一个编译器搬到一台新机器上，要重写多少？

编译器的语言

编译器的实现语言（或称主机语言，host language）当然可以是机器语言——最早的编译器就是这么写的。另一种做法是用另一种已经有编译器的语言来写新编译器：只要用已有的编译器编译一下新编译器，就得到了一个能运行的程序。

但如果已有的编译器运行的机器和目标机器不同呢？这时编译产生的是一个交叉编译器（cross compiler）——为另一台机器生成目标代码的编译器。为了把这些情形说清楚，我们需要一种图。

情形 1：串联两个编译器

同一台机器 H 上有两个编译器，一个把 A 翻译成 B，另一个把 B 翻译成 C。让第一个的输出成为第二个的输入，就得到了 H 上从 A 到 C 的编译器。

情形 2：用一个编译器翻译另一个编译器

更有意思的情形：我们有一个从"机器" H 到"机器" K 的编译器 M，可以用它把另一个编译器的实现语言从 H 翻译成 K。读图的方法：上面左边的 T 是被翻译的编译器（它是用 H 写的程序），下面的 T 是做翻译的编译器（源语言 H 正好对上），右边是结果——同样的编译器，但现在用 K 写成、运行在 K 上。

用已有的编译器造新编译器

交叉编译器

给定：机器 K，以及一个用 K 写的、把 B 翻译成 K 的编译器。想要：语言 A 的编译器，目标语言是 H（另一台机器）。做法一样——用 B 写一个 A → H 的编译器，在 K 上编译它。结果是一个运行在 K 上、却为 H 生成代码的编译器，这就是交叉编译器。

H = S：鸡生蛋的问题

现在问一个尖锐的问题：能不能用一门语言写它自己的编译器？比如用 C 写 C 编译器。麻烦在于：源语言的编译器还不存在，所以这个编译器本身没法被编译。这里有一个循环：

自举

解决办法叫自举（bootstrapping，"拽着自己的鞋带把自己提起来"），分三步：

  1. 用汇编语言写一个"快而糙"（quick and dirty）的 A 编译器——功能够用就行，生成的代码可以很差。
  2. 用这个粗糙的编译器编译"好的"编译器（用 A 自己写的那个）。得到的编译器功能完整，但因为是粗糙编译器生成的，它本身运行得慢。
  3. 用第 2 步得到的编译器再编译一次"好的"编译器。这一次，编译器的代码是由"好的"编译器生成的，于是得到了最终版本：功能完整、而且高效。

补充：自举的阴影——"信任信任"

1984 年，UNIX 之父 Ken Thompson 在图灵奖演讲《Reflections on Trusting Trust》中指出自举的一个惊人后果：如果有人在某一代 C 编译器里植入一段代码，让它在编译 login 程序时偷偷加入后门，并且在编译编译器本身时把这段植入代码也复制进去——那么即使把源代码里的恶意部分删得一干二净，用被污染的编译器编译出来的新编译器仍然带毒。你读遍所有源代码也发现不了它。这个思想实验说明：编译器是整个软件信任链的根。

1.7　TINY 语言与 TM 机器

真实机器上的真实编译器细节太多，本课程用一门小语言 TINY 作为贯穿全课的例子，目标代码是一台简单的假想处理器 TM 机器的汇编语言。

TINY 语言

  • 程序是用分号分隔的语句序列；没有过程，没有声明。
  • 所有变量都是整数，通过赋值来"声明"。
  • 两种控制语句：if 语句（可带 else，必须以关键字 end 结束）和 repeat … until 语句。
  • read 和 write 语句用于输入输出。
  • 注释写在花括号 { } 里。
  • 算术表达式包含整数常量、变量、括号和四种整数运算 + - * /。
  • 布尔表达式是两个算术表达式用比较运算符 < 或 = 连接而成，只能出现在控制语句的测试位置。
  • 赋值运算符是 :=。
{ Sample program
  in TINY language -
  computes factorial
}
read x; { input an integer }
if 0 < x then { don't compute if x <= 0 }
  fact := 1;
  repeat
    fact := fact * x;
    x := x - 1
  until x = 0;
  write fact  { output factorial of x }
end

计算阶乘的 TINY 程序。注意 repeat 循环体内最后一条语句后面没有分号——分号是分隔符而不是终止符。

TM 机器

TM 具有 RISC 处理器的一些特性：所有的算术和测试都必须在寄存器中进行；寻址方式很有限。地址的形式是"寄存器 + 偏移量"：10(1) 表示"寄存器 1 的内容加上偏移量 10"所得的地址。三条装入指令：LDC（load constant，装入常数）、LD（load，从内存装入）、LDA（load address，装入地址）。

课件用 a[index] = 6 演示 TM 代码，假设 index 在内存位置 10，a 在内存位置 20（这次每个整数占 1 个内存单元，所以乘 2 是为了演示，而不是元素大小）：

指令作用
LDC 1,0(0)把常数 0 装入寄存器 1（清零，准备当基址）
LD 0,10(1)把地址 10 + R1 = 10 处的值（即 index）装入 R0
LDC 1,2(0)把常数 2 装入 R1
MUL 0,1,0R0 = R1 × R0（index 乘 2）
LDC 1,0(0)再次把 0 装入 R1
LDA 1,20(1)把地址 20 + R1 = 20（a 的基址）装入 R1
ADD 0,1,0R0 = R1 + R0，得到 a[index] 的地址
LDC 1,6(0)把常数 6 装入 R1
ST 1,0(0)把 R1 存到地址 0 + R0 处（即 a[index]）

把这段代码和 1.3 节的五条指令对照，可以清楚看到"寻址方式有限"的代价：TM 没有 MOV *R1, 6 这样的间接寻址，只能老老实实先把常数装进寄存器再存储；连"把 0 装入寄存器"都要单独一条指令。第 8 章学代码生成时，你会亲手为 TINY 生成这样的代码。

小结与作业

本章小结

  • 编译器把源语言程序翻译成等价的目标语言程序。它的出现源于机器语言 → 汇编 → 高级语言的阶梯，理论基础是乔姆斯基层次（单词用 3 型、语法用 2 型）。
  • 编译器的亲戚：解释器（边翻译边执行）、汇编器、连接器、装入程序、预处理器、编辑器/IDE、调试器、描述器。
  • 六个阶段：扫描（字符→记号）、分析（记号→树）、语义分析（树→注释树）、源代码优化（→中间代码）、代码生成（→目标代码）、目标代码优化。三个共享组件：常数表、符号表、错误处理器。
  • 主要数据结构：记号（枚举 + 属性）、语法树（指针结构）、符号表（哈希表）、常数表、中间代码、临时文件。
  • 分析 vs 综合；前端 vs 后端（可移植性，M + N）；遍 ≠ 阶段；语言定义；出错处理。
  • T 型图的两种拼接；自举三步；移植 = 改代码生成器 + 两次编译。
  • TINY：无声明、全整数、if/repeat、read/write；TM：寄存器 + 偏移量寻址，LDC/LD/LDA。
